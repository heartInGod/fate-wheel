# fate-wheel —— 自动进化的 AI 证券经理

> 一个会自己分析数据、盯盘出信号、收盘复盘、管理仓位，并且每天都在自我校准、越用越准的 AI 证券经理。Python 规则引擎算确定性部分，大模型做语义判断，微信（可切飞书）把结论推到手机。**只给建议、不自动下单。**

## 一、产品能力

| 能力 | 说明 |
|---|---|
| 数据分析 | 自动采集并分析行情、资金流、公告、新闻、估值、行业景气、政策信号，多源聚合、官方优先 |
| 盯盘信号 | 盘中每 10 分钟把盯盘规则量化成可执行信号：加仓 / 做T / 减仓止损 / 异动 / 自选低吸，每条带价格区间、数量、期望收益 |
| 复盘分析 | 收盘自动给每条建议打分，判断对错、执行偏差一目了然，并沉淀成经验 |
| 仓位管理 | 双仓制：长线仓按估值目标价低买高卖，交易仓量化短线低频操作；仓位和阈值每天自动校准 |
| 自动进化 | 每天用近 40 个交易日的历史回放引擎校准参数，用三套记忆修正判断，越用越贴合市场 |

## 二、典型使用场景

### 场景 1：开盘前 —— 拿到今天的操作计划

09:00 自动生成盘前分析：核实持仓逻辑是否还成立，给出支撑 / 压力位、当日操作区间，以及长线 / 交易两仓各自怎么应对。

### 场景 2：盘中 —— 每 10 分钟盯盘，有信号才提醒

盘中每隔 10 分钟扫一遍：规则引擎先算候选，大模型再逐条判断，**只在出现新的可执行信号时才推通知（默认微信）**——不刷屏，有动作才提醒。

### 场景 3：收盘后 —— 自动复盘，越用越准

16:00 自动给当天每条建议打分，校准次日阈值、更新经验。今天哪条判断对了、哪条错了，第二天开始就带着教训工作。

### 场景 4：每周五 —— 长线仓体检

每周五自动复查长线持仓：估值目标价还成不成立、政策和景气有没有变化、要不要调整仓位。

## 三、基本架构

```
┌──────────────────────────────────────────────┐
│          Agent 层（大模型 · 定时任务）           │
│   盘前 / 盘中 / 收盘 / 评估 / 周报，逐条判断信号   │
└──────────────────────┬───────────────────────┘
                       │ 读候选 · 写判断 · 读经验
┌──────────────────────▼───────────────────────┐
│       分析与决策层（Python）                    │
│   规则引擎 · 估值 · 仓位 · 校准 · 复盘 · 经验沉淀 │
└──────────────────────┬───────────────────────┘
                       │ 读快照 · 写参数
┌──────────────────────▼───────────────────────┐
│         数据层（Python · 公开网页接口）          │
│   行情 · 资金 · 公告 · 新闻 · 估值 · 商品        │
└──────────────────────────────────────────────┘
```

数据流一句话：**采集 → 规则引擎算候选 → Agent 判断 → 通知提醒（微信/飞书） → 收盘复盘 → 校准 / 沉淀经验 → 反哺下一轮**。

系统运行日志（每步的耗时/阶段/异常）独立写在 `logs/YYYY-MM-DD/ops.log`，与上面的业务结论日志隔离，排障用 `python3 main.py logs tail 50`（详见 `DATA_SOURCES.md`「系统运行日志」）。

## 四、与 Agent 结合的设计亮点

核心思路：**不是让大模型自己看行情发挥，而是把决策拆成「机器能算准的」和「机器算不准的」两部分，分别交给 Python 和 Agent，再用闭环咬合起来。** 这套分工的最终结果，就是它能「自动进化」。

### 亮点 1：确定性引擎先算，大模型后判断

规则引擎先把定性规则量化成候选（价格、数量、扣费后期望收益、胜率、市场状态），大模型只做算不了的语义判断——公告利空是否让支撑失效、板块资金配不配合、量能放不放大。各干各擅长的，判断被约束在可执行框架里，不会拍脑袋。

### 亮点 2：每个判断都能被「打分」，复盘形成闭环

每条信号结构化落盘（候选 → 采纳 / 否决 → 发送），收盘统一打分——**连被否决的候选也打分**。于是「该采纳却否决了」「该否决却采纳了」都会暴露出来，判断质量每天有胜率、有 edge，而不是靠感觉。

### 亮点 3：每天自我校准，参数自动进化

每天收盘用近 40 个交易日的历史数据回放引擎，自动调阈值、期望收益、仓位。大模型每天拿到的候选，都是前一天用真实数据调过的，越用越贴合市场。

### 亮点 4：三套记忆，判断自动进化

- **经验文档**：复盘沉淀的经验条目（观察 → 验证 → 生效 → 作废），每次判断前必读，命中就按经验办。
- **定位前提**：每只持仓的持有逻辑，判断时只能引用「成立」的前提，杜绝用过期的逻辑当依据。
- **当日日志**：盘中读盘前判断，保证同一天的信号前后一致。

### 亮点 5：对比「全部直接丢给大模型」—— 当前项目的优势

| 维度 | 全部丢给大模型 | 当前项目（Python + Agent 分工） |
|---|---|---|
| 数字准确性 | 算术（手续费 / 期望收益 / 仓位）易错易编 | Python 算，可验证可复现 |
| 可复现性 | 每次问结果可能不同 | 同输入同候选，判断过程落盘可查 |
| 可评估性 | 自由文本无法对齐打分 | 每条信号结构化、收盘统一打分 |
| 持续改进 | 只能改 prompt | 校准 + 打分 + 经验三套闭环 |
| 成本 / 稳定 | token 贵、慢、易超时 | Python 秒级算，大模型只做增量 |
| 单点依赖 | 押在单一模型能力 | 规则引擎可独立验证、模型可替换 |

一句话：**大模型擅长「理解」，不擅长「算准」和「负责」。** 本项目把「算准」交给 Python、把「负责」交给闭环、只把「理解」留给 Agent——于是它既懂市场，又算得准、可追责，还能越用越聪明。

## 五、快速开始

```bash
cd fate-wheel
./setup.sh                                          # 一次性配置（含派生 setup/minimax/ 定时任务定义）
python3 main.py fetch snapshot mode=intraday        # 手动验证数据
python3 main.py signals --no-record               # 预览候选信号
python3 main.py market                             # 大盘资金面（宽度/成交额/主力/两融/外盘 + 冰点闸门）
fate wheel                                          # 生成数据并打开看板（也可直接双击根目录 dashboard.html）
```

> ⚠️ 所有提醒仅供个人研究参考，不构成投资建议；系统不自动下单。

## 六、定时任务（MiniMax Code）

7 条定时任务托管在 **MiniMax Code 原生定时任务（cron）**，定义在 `setup/minimax/`：

| 时间 | 任务 | cron 表达式 |
|---|---|---|
| 每天 09:00 | 盘前分析（含周末，prompt 内判断休市） | `0 9 * * *` |
| 工作日 09:45 | 盘中分析 | `45 9 * * 1-5` |
| 工作日 10/13/14 点每 10 分钟 | 盘中分析 | `0,10,20,30,40,50 10,13,14 * * 1-5` |
| 工作日 11:00–11:30 | 盘中分析 | `0,10,20,30 11 * * 1-5` |
| 工作日 15:00 | 收盘分析 + 收盘小结 | `0 15 * * 1-5` |
| 工作日 16:00 | 收盘建议评估 + 参数校准 + 经验更新 | `0 16 * * 1-5` |
| 周五 17:00 | 长线仓复查 + 政策周报 | `0 17 * * 5` |

- `setup/crons.json` 是 prompt 的唯一来源；改完跑 `python3 setup/minimax/_generate.py` 重新派生
  `setup/minimax/tasks.json` 与 `setup/minimax/prompts/*.txt`，MCode 里的任务下次运行自动用新 prompt（无需重建任务）。
- MCode 跑在 Windows、项目在 WSL，所有 prompt 都带统一的「运行环境」头，命令经 `wsl.exe -e bash -lc` 执行。
- 只有改**调度时间或模型**才需要在 MCode 里更新对应任务（详见 `setup/minimax/README.md`）。
